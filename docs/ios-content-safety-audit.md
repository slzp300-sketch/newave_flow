운영자는 앱의 안전 관리 현황을 정기적으로 확인하고 긴급 신고를 우선 처리해야 한다. 이 기능 준비를 Apple 1.2의 심사 승인이나 실제 운영 대응 완료로 표현하지 않는다. 개인별 차단 목록은 제공하지 않으며 내부 업무 자료의 권한과 관리자 계정 정지로 접근을 제어한다. 실제 iPhone의 최종 기능 검수와 제출 주체 확인은 별도 남는다.

## 초기 점검 기록 — 위 후속 구현 전 상태

Apple [App Review Guidelines 1.2](https://developer.apple.com/app-store/review/guidelines/#user-generated-content)는 게시 전 유해 콘텐츠 필터, 신고와 적시 대응, 가해 사용자 차단, 공개 연락처를 요구한다. 이 문서의 기능별 우선순위는 해당 기준과 현재 코드의 차이를 검토한 결과이며 심사 결과를 보장하지 않는다.

- 이용수칙: `CommunitySafetyConfig`가 서버의 작성 요청에 현재 버전 동의를 요구한다. `CommunitySafetyService`는 계정별 동의 버전·시각을 저장한다. 동의 자체는 게시 내용을 검사하는 필터가 아니다.
- 신고: 콘텐츠·사용자 신고, 신고자 자신의 내역, 관리자 검토·결과 안내, 중복 접수 방지, 접수 제한, 대상 열람 권한 검증이 있다. 신고는 동의 전에도 가능하다.
- 관리자 조치: 회의록 비공개와 사용자 정지를 실행할 수 있다. 정지는 `User.suspend()`의 비활성화·인증 버전 변경을 통해 기존 세션도 폐기한다.
- 회의록: 관리자 역할은 `ADMIN`, `PASTOR`, `EXECUTIVE`이다. 일반 교사는 공개 목록을 읽고 자신의 확인 상태를 남긴다. 관리자는 수정·삭제·공개 전환을 할 수 있다.
- 연락처: 로그인 전에도 접근 가능한 고객지원·개인정보처리방침에 운영자 연락 방법이 있다.
- 기존 회귀 근거: `CommunitySafetyHttpTest`는 동의, 신고 비밀 유지, 대상 접근 범위, 비공개 처리, 사용자 정지, 권한 상승 방지, 중복 접수와 제한을 검증한다.

## 이번에 보완한 회의록 접근 경계

`MeetingMinuteController`의 `GET /api/minutes/{id}/status`는 교사별 이름·출석·불참 사유·확인 시각을 반환하면서 별도 관리자 권한 검사가 없었다. 기본 보안 설정은 인증만 요구하므로 일반 교사에게도 열릴 수 있었다. 실제 자료를 조회하지 않고 코드로 확인했다.

- 관리용 현황은 `ADMIN`, `PASTOR`, `EXECUTIVE`만 접근하도록 제한했다. 일반 교사는 공개·비공개·없는 ID 모두 403을 받아 관리용 현황의 존재를 확인할 수 없다.
- 확인 POST는 현재 계정이 목록에서 볼 수 있는 회의록에만 허용한다. 일반 교사가 비공개 또는 없는 ID를 요청하면 같은 404를 반환한다. 관리자는 기존 관리 목록과 동일하게 비공개 회의록도 확인할 수 있다.
- 공개 회의록의 교사 조회, 본인 확인 저장, 중복 확인의 동일 결과는 유지한다. 요청의 사용자 ID로 다른 사람을 확인 처리하지 않는다.
- 별도 상세 GET 및 확인 취소 DELETE는 현재 구현되어 있지 않다. 상세 본문은 권한별 목록에 포함되며 이번 수정에서 새 경로를 만들지 않았다.
- 회의록 작성 요청 전체를 출력하던 디버그 로그도 제거해 본문이 서버 로그에 남지 않도록 했다.
- 관련 파일: `backend/src/main/java/com/newaveflow/controller/MeetingMinuteController.java`, `backend/src/test/java/com/newaveflow/MeetingMinuteAuthorizationHttpTest.java`.
- 전용 회귀 검증: `MeetingMinuteAuthorizationHttpTest` 7건과 기존 `CommunitySafetyHttpTest` 6건이 로컬 H2에서 모두 통과했다(2026-10-15, 실패·오류·건너뜀 0건). 테스트는 가상 계정·회의록·불참 사유만 사용한다. 전체 서버 회귀 검사와 배포 검증은 별도 단계이다.

## 초기 점검에서 확인한 보완 사항

### P1 — 게시 전에 적용되는 필터

현재 이용수칙 동의를 받으면 회의록 본문·일정 설명·공동 보고 특이사항·프로필 입력을 그대로 저장한다. 유해 텍스트 검사나 검토 대기 절차는 확인되지 않았다. 승인된 교사 계정만 사용할 수 있다는 사실은 개별 게시물의 검사를 대신하지 않는다.

- 근거: `MeetingMinuteController.create/update`, `EventService.create/update`, `ReportService.saveOrUpdate`, `UserController.updateProfile`, `CommunitySafetyConfig`.
- 보완: 공유되는 자유 입력 필드의 범위를 먼저 정하고 서버의 생성·수정 경로에 공통 검사를 적용한다. 명확한 위협·혐오·성적 표현 등을 걸러내는 규칙과 애매한 경우의 관리자 검토 절차를 함께 설계한다. 단순 금칙어 목록만으로 모든 유해 콘텐츠를 막는다고 주장하지 않는다.
- 사진은 텍스트 필터의 보호를 받지 않으므로 별도 검토 대기·거절·삭제 방식을 정한다. 기존 업무 사진·동의·권한과 충돌하지 않아야 한다.
- 학생·종교·건강 관련 원문을 외부 검사 서비스로 자동 전송하는 방식은 선택하지 않았다. 필요하다면 최소 전송 범위, 처리 근거, 외부 제공·위탁 안내를 별도로 검토한다.
- 테스트: 신규·수정·구버전 클라이언트의 직접 API 요청도 검사, 문자 정규화·공백 삽입 우회, 정상 업무 문구의 오탐, 거절 시 원문·인증정보 로그 유출 방지, 사진 승인 전 일반 사용자 미노출.

### P1 — 정지 계정과 신규 승인 대기 분리

`User.suspend()`는 `isActive=false`만 남긴다. `AdminUserService.getPendingUsers()`는 비활성 계정을 모두 신규 승인 대기로 반환하며, `approveUser()`는 정지 사유나 복구 담당자의 권한을 구분하지 않고 다시 활성화한다. 관리자가 제재한 계정이 가입 대기 화면에서 일반 승인될 수 있다.

- 근거: `User.suspend/approve`, `AdminUserService.getPendingUsers/approveUser`, `AdminUserController`, `frontend/src/pages/AdminPendingUsersPage.jsx`.
- 보완: 가입 대기와 운영상 정지를 구분하고 정지 사유·처리 시각을 유지한다. 정지 복구는 별도 권한과 확인 절차로 처리하며 일반 가입 승인 API로 우회하지 못하게 한다.
- 사용자 개인의 차단 목록·상대 콘텐츠 숨김 UI는 없다. 그러나 관리자 정지는 실제 서비스 접근을 막으므로 차단 기능이 전혀 없다고 설명해서는 안 된다. 개인별 차단이 필요한 상호작용 범위와 공용 업무 자료의 열람 범위를 함께 결정한다.
- 테스트: 정지 계정의 가입 대기 제외, 일반 승인 우회 거부, 역할별 정지 복구 제한, 본인 복구 불가, 이전 세션의 계속된 거부, 적법한 복구 후 새 로그인.

### P2 — 신고 대상과 실제 보호 조치의 연결

`ContentReport.ContentType`은 회의록·공동 보고·기타를 구분하지만 신고 처리 API의 직접 콘텐츠 조치는 회의록 비공개에 집중돼 있다. 공동 보고·기타 사진은 신고 처리 화면에서 실제 내용을 제거하는 대신 `REVIEWED` 결과만 기록할 수 있다. 다른 업무 화면의 수정 기능이 있더라도 신고 대상 확인과 실제 조치가 분리돼 있어 빠뜨릴 가능성이 있다.

- 근거: `ContentReport.Action`, `CommunitySafetyService.resolve`, `ContentReportsAdminPage`의 조치 목록, `ContentReportPage`의 기타 대상 자유 입력.
- 보완: 각 공유 콘텐츠의 안정적인 대상 ID·열람 권한·관리 화면 연결을 제공한다. 대상별로 숨김·부분 수정·삭제 등 적절한 보호 조치를 연결하고 실제 처리 결과와 신고 상태가 일치하도록 한다. 공동 기록 전체를 일괄 삭제해 다른 구성원의 자료가 손상되지 않게 한다.
- `MeetingMinutesPage`는 처음 읽은 목록과 선택 객체를 보관한다. 공개된 회의록을 나중에 비공개로 바꿔도 이미 열린 화면에는 이전 내용이 남을 수 있다. 앱 복귀·재조회·조치 직후 대상의 최신 공개 상태를 확인하고 더 이상 볼 수 없는 열린 내용을 닫는다.
- 테스트: 대상별 조치 후 실제 노출 변화, 없는 대상·권한 없는 대상 처리 거부, 처리 완료 기록만 있고 보호 조치가 빠지는 경우 방지, 이미 열린 모달의 재조회 후 제거, 다른 구성원의 자료 보존.

### P2 — 신고에 적시에 대응할 운영 경로

신고 접수는 저장만 수행한다. 관리자 화면에 접수 시각과 상태는 있지만 담당자·응답 목표·기한 초과 표시가 없다. 기존 `NotificationService`는 기본 비활성이며 신고 접수와 연결되어 있지 않다. 담당자가 신고 목록을 직접 열지 않으면 긴급 신고가 누락될 수 있다.

- 근거: `CommunitySafetyService.create/resolve`, `ContentReportsAdminPage`, `NotificationService`의 `NOTIFICATIONS_ENABLED:false`.
- 보완: 운영 가능한 확인·처리 목표를 정하고 관리자 홈의 미처리 표시, 접수 경과·긴급 분류·담당자·처리 안내를 연결한다. 기존 알림 기능을 재사용하려면 비활성 설정과 수신 대상까지 검증한다. 기한 숫자를 정하는 것만으로 실제 응답을 보장하지 않는다.
- 테스트: 관리자만 미처리 현황 확인, 신고자·내용 노출 최소화, 재전송으로 중복 알림이 생기지 않음, 기한 초과 표시와 처리 후 해제, 신고자의 처리 안내 열람.

## 제출 준비 시 확인할 범위

위 네 가지 항목의 구현은 문서 상단의 후속 결과를 따른다. 운영 담당자의 대응과 실제 기기 검수는 별도로 확인한다. 현재 상태를 Apple 1.2 충족 완료로 기록하지 않는다. Apple 로그인 활성화 전의 개인정보처리방침·App Store 개인정보 신고 보완은 `docs/ios-apple-sign-in.md`에 따른다. 실제 Apple 계정·실기기·TestFlight 검수는 별도 남은 단계이다.
