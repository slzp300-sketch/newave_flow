# 일정 확인 상태의 계정 동기화 (2026-10-12)

## 동작

- 홈에서 일정 내용을 펼치거나 달력의 ‘내용 확인했어요’를 누르면 로그인한 계정의 확인 기록을 저장한다. 확인이 성공한 뒤 빨간 점을 해제한다.
- 같은 계정의 다른 기기에서 화면을 열거나 다시 돌아올 때 조회하며, 활성 화면에서는 15초 주기로 확인 상태를 갱신한다. 인터넷 연결이 필요하며 푸시 방식의 즉시 동기화는 아니다.
- 일정의 제목·설명·날짜·시간·분류·색상·출석 여부/마감/대상이 달라지면 다시 표시한다. 종료된 일정은 알림에서 제외한다. 내부 명단 캡처나 출석 제출은 일정 내용 변경으로 취급하지 않는다.
- 기존 브라우저의 사용자별 확인 기록은 현재 내용과 일치할 때만 서버에 이전한다. 이미 바뀐 일정은 미확인으로 유지한다. 이전 기록이 남은 브라우저에서 해당 일정을 열어야 이전할 수 있다.
- 저장 실패 시 미확인 상태와 안내를 유지한다. 이전 내용을 본 기기의 요청은 409로 거절하고 최신 일정을 다시 조회한다. 조회 실패는 완료로 단정하지 않는다.

## API와 데이터

- `GET /api/event-reads`: 인증 계정의 `{일정ID: 내용버전}`. 다른 계정 ID를 지정하는 기능 없음.
- `PUT /api/event-reads/{eventId}`: `{version: SHA-256 64자리}`. 서버 현재 내용과 대조하고 한 계정·한 일정에 한 기록만 저장한다. 중복 요청은 같은 결과이며 일정 행 잠금으로 동시 최초 저장 충돌을 막는다.
- 일정 응답에 `readVersion` 추가. 일정 내용의 정해진 필드 배열로 계산하며 변경 시 DB의 모든 사용자 기록을 일괄 수정할 필요가 없다.
- `event_reads(user_id, event_id, content_version, read_at)`는 계정·일정 삭제 시 함께 정리된다. 참석 기록이나 출결보고/TTS 점수는 변경하지 않는다.
- 별도 확인 API를 사용하므로 확인할 때 출석·행사·TTS 화면 전체를 무효화하거나 다시 로딩하지 않는다. 늦게 도착한 조회 결과가 확인 성공을 덮어쓰지 않도록 조회를 취소한 뒤 캐시를 합친다.

## 검증과 배포

1. DPAPI 암호화 백업을 만든 뒤 별도 PostgreSQL 18에 복원한다. 전체 33개 테이블의 건수·해시를 백업 시점과 대조한다.
2. `EventReadMigrationTest`에 `RUN_EVENT_READ_MIGRATION=true`, 로컬 `newave_migration_eventreads_*` DB 및 환경변수를 전달한다. V002 실패 시 전체 롤백, 정상 적용 후 기존 모든 테이블 해시 보존, 재적용 차단, 새 앱의 `prod/ddl-auto=validate` 시작을 검사한다. 이 검사는 V001을 다시 실행하지 않는다.
3. 기존 `PostgresMigrationTest`는 V001 다음 V002도 검증한다. 가상 계정 두 요청의 동시 확인/중복 방지와 기존 출석·행사·TTS 업무를 PostgreSQL에서 검사한다. CI는 PostgreSQL 17/18에서 실행한다.
4. `EventReadTest`와 `EventReadHttpTest`에서 다른 계정 분리, JWT 인증, 사용자 ID 위조 무시, 입력 검증, 내용 변경 충돌, 삭제 정리, 표시 필드별 버전 변경을 검사한다. 프런트 검사·운영 빌드와 375px 실제 컴포넌트/가상 서버 화면도 확인한다.
5. **V002는 기존 구조를 바꾸지 않는 추가 테이블 전환**이다. 검증한 `V002__account_event_reads.sql`만 운영에 먼저 적용한다. V001의 서비스 중지·데이터 병합 절차를 재실행하지 않는다. 짧은 잠금 제한/트랜잭션/스키마 잠금을 사용하며 기존 앱은 계속 동작한다.
6. V002 적용 후 main 배포, 새 백엔드 스키마 검증·정상 시작, 프런트와 CI/PWA 버전을 확인한다. 두 배포 시점이 어긋나면 구버전 서버에서는 읽음 기능이 잠시 미제공일 수 있고 실패 안내를 표시한다.
7. 앱 롤백 시 V002 테이블을 남겨도 이전 앱과 호환된다. 기존 업무 데이터를 백업으로 덮어쓰거나 확인 기록을 삭제할 필요가 없다. SQL 자체 실패는 커밋 전에 롤백된다.

정기 백업은 public의 모든 테이블을 포함하므로 새 확인 기록도 다음 백업부터 함께 보관된다. 실제 계정의 운영 확인 버튼을 시험 삼아 누르지 않으며, 저장 검수는 가상 계정과 별도 환경에서 수행한다.
