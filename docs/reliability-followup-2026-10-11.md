## 1. 출석·TTS 조회 실패 시 입력 보호 — 완료

- 출석의 담당 반·학생·출석 기록·반 공동 제출 상태를 모두 읽은 뒤에만 입력·제출을 허용합니다.
- TTS 질문과 주간 기록 중 하나라도 실패하면 체크·점수를 숨기고 오류와 재시도를 표시합니다. 실제 0점과 조회 실패를 구분합니다.
- 처음 읽는 중, 재조회 중, 오프라인으로 요청이 멈춘 경우도 입력을 잠급니다.
- 출석 입력은 반·날짜별 초안으로 관리합니다. 주차를 바꾸면 이전 주 초안을 새 주에 제출할 수 없습니다. 같은 주의 재조회는 작성 내용을 유지합니다.
- 출석 제출 중에는 주 이동·입력을 잠급니다. TTS 저장 중에는 주 이동을 잠그고, 저장·실패 복원은 요청 당시 주차에 적용합니다.
- TTS 통계 조회 실패도 기록 없음과 구분합니다.

가상 503 장애에서 제출/체크가 없음을 확인했습니다. 재시도 후 기존 결석 사유·메모·TTS 월요일 체크와 5점이 복원됐습니다. 이전 주로 이동한 뒤의 조회 실패도 같은 방식으로 차단됐습니다.

## 3. 마감 안내 — 완료 및 앞선 분석 정정

앞선 보고서는 저장 요청을 구성하는 코드의 종료일 자동 대입을 빠뜨렸습니다. 실제 규칙은 다음과 같습니다.

- 개별 일정 폼: 마감일을 비우고 저장하면 일정 종료일을 마감일로 자동 대입합니다.
- 일괄 일정 폼: 출석이 필요한 행사는 종료일을 마감일로 저장합니다.
- 이미 저장된 행사: 명시적 마감일이 있으면 그날까지 제출 가능하고, 없는 기존 행사는 기한을 제한하지 않습니다.

업무 규칙을 바꾸지 않고 개별 일정 폼에 **저장할 때 종료일로 자동 설정됨**을 명시했습니다. 마감일이 없는 행사 출석 화면에는 **제출 기한 제한 없음**을 표시했습니다. 기존 행사에 새 마감일을 일괄 부여하지 않았습니다.

마감 당일/다음 날, 월말·연말, 마감일 없음, 화면을 열어 둔 뒤 날짜 변경의 기존 자동 검사를 통과했습니다.

권장안은 앱 사용 전 기간의 시트 총점을 당시 기록으로 보존하고, 앱 사용 시작 이후 기록은 별도로 대조하는 것입니다. 실제 전환 주차와 위 2건의 기준 점수 확인 후 미리보기·건수·합계 대조를 거쳐 가져옵니다. 휴회 여부의 불확실성은 원본 값을 그대로 보존하는 이관 준비를 막는 조건으로 두지 않되, 휴회 주차의 통계 제외 여부는 별도 정책으로 확정해야 합니다.

2026-10-11 사용자는 출석·행사를 매번 단체 대화방의 텍스트로 공유·수정해 왔으며 명확한 원본 시트가 없다고 설명했습니다. 따라서 **확정 원본 부재로 외부 원본과의 일치 여부를 검증할 수 없음**으로 정리하고, 원본 시트 제출 대기는 종료합니다. 현재 DB의 기록 보존·집계 일치·반별 공동 완료·저장 후 재조회 검증을 기준으로 삼습니다. 기존 검수는 기능과 DB 보존을 확인한 것이며 실제 당시 출석의 사실성까지 입증한 것은 아닙니다. 이후 특정 날짜의 확정된 대화방 기록을 제공받으면 그 범위만 추가 대조할 수 있습니다.

## 8. 역할·로그인·느린 연결 검수 — 확인 범위 통과

가상 서버의 실제 HTTP 검증 40개가 통과했습니다. 정상/거절 상태뿐 아니라 거절 후 기존 기록이 바뀌지 않았는지도 확인했습니다.

- 일반 교사의 다른 반 출석·보고서 제출·행사 학생 수정은 403으로 거절됩니다. 자기 반 요청에 다른 반 학생을 끼우면 400으로 거절됩니다.
- 일반 교사는 관리자 출석/TTS/행사 집계 및 행사 수정·권한 변경을 사용할 수 없습니다.
- ADMIN·PASTOR·EXECUTIVE의 허용된 집계 접근은 성공합니다. PASTOR·EXECUTIVE의 ADMIN 부여/변경과 EXECUTIVE의 관리자 비밀번호 초기화는 거절됩니다.
- 미래 출석과 미래 TTS 입력을 거절합니다.
- 검수 서버의 접근 토큰 유효 시간을 15초로 줄였습니다. 만료 요청 401 → 갱신 200 → 재요청 200을 실제 API와 브라우저에서 확인했습니다. 로그아웃한 갱신 토큰은 401, 브라우저는 로그인 화면으로 이동합니다.
- 8초 느린 TTS 저장 중 주차 이동이 잠깁니다. 연속 입력은 기존 직렬 저장 큐를 사용합니다. 느린 저장 성공 후 25점이 유지됩니다.
- TTS 저장 요청을 검수 프록시에서 503으로 실패시켜 오류 안내와 30→25점 복원을 확인했습니다. 실패한 목요일 체크는 남지 않습니다.
- 처음 읽는 주차의 조회를 8초 지연하면 입력과 점수 대신 로딩 안내를 표시하고, 성공 후 체크 화면이 복구됩니다.
- 375px TTS·로그인 화면에서 가로 넘침이 없었습니다. 브라우저 콘솔에는 React Router의 향후 버전 안내만 있었고 새 런타임 오류는 없었습니다.

이 검사는 대표 경로와 권한 경계에 대한 검증입니다. 모든 API의 전수 보안 감사나 실제 iPhone/Android의 설치형 앱 검증은 아닙니다. PWA 업데이트의 첫 설치·두 탭·입력 보존은 위 4절의 이전 검증 결과를 유지하며, 이번에 같은 검사를 중복 수행하지 않았습니다. EXECUTIVE가 관리자 업무 대부분에 접근하는 현행 범위는 사용자 정책 결정 사항으로 남습니다.

## 9. 백업·복원 — 복원 성공, 정기 백업 미설정

- Railway 공개 API에서 운영 PostgreSQL 볼륨의 백업 스케줄 목록은 빈 배열이었습니다.
- Railway CLI의 시점 복구(PITR) 상태도 `enabled=false`, `bucketWired=false`였습니다. 연속 백업이 대신 작동하는 상태도 아닙니다.
- 백업 목록에는 `Pre-Security-Patch Backup` 1건이 반환됐습니다. 생성은 2026-08-23 20:00 한국 시간, 만료는 2026-09-22 20:00 한국 시간으로 현재 만료 시각이 지난 상태입니다. 이 항목의 실제 복구 가능성은 확인되지 않았습니다.
- 10월 10일 20:53의 로컬 `pg_dump` 파일(174,777바이트)은 PostgreSQL 18의 새로운 별도 DB로 복원했습니다. 원본 28개 테이블을 읽을 수 있었고, 전환 후에도 출석·행사 출석·TTS 6개 테이블의 행 해시가 유지됐습니다. 현재 앱의 `prod/validate` 기동과 읽기 전용 TTS 통계 계산까지 성공했습니다.
- 이 로컬 백업은 10월 10일 이후의 입력을 포함하지 않습니다. 저장소 업로드·운영 복원·운영 설정 변경은 하지 않았습니다.

다음 우선 조치는 **일간·주간·월간 정기 백업 활성화와 첫 백업 성공 확인**입니다. Railway 문서의 보존 기간은 각각 6일·27일·89일이며, 백업 저장량에 따른 비용이 발생합니다. 아직 활성화하지 않았습니다. [Railway 백업 정책](https://docs.railway.com/volumes/backups), [PostgreSQL 백업 안내](https://docs.railway.com/guides/postgres-backups-restores).

복구 순서는 입력 중지 → 최신 상태를 별도로 백업 → 대상 백업을 분리된 환경에 복원 → 스키마 버전·주요 행 해시/건수·로그인/출석/행사/TTS 확인 → 백업 이후 추가 입력 보존·재반영 계획 수립 → 운영 전환입니다. 전환 전 백업에는 이전 스키마가 있으므로 새 앱을 바로 연결하지 않습니다. 필요한 전환을 복원본에 먼저 적용하고, `V001`이 이미 적용된 DB에는 다시 실행하지 않습니다. 상세 기준은 `deployment-checklist.md`를 따릅니다.

## 범위 변경 전 후속 항목 — 아래 10절의 최신 계획으로 대체

1. 정기 백업 설정과 첫 백업 확인.
2. TTS는 3/39주차를 휴회 추정으로 기록하고 원본 값을 보존. 앱 전환 주차와 겹친 점수 2건의 기준을 확정한 뒤 가져오기 미리보기·대조·이관. 휴회 주차의 통계 제외 여부는 별도 확정.
3. 출석·행사의 원본 시트 대기는 종료. 현재 DB의 보존·집계·공동 완료 검증을 유지하며, 추후 확정된 날짜별 자료가 생기면 해당 범위만 추가 대조.
4. 실제 Android/iPhone 설치형 앱의 업데이트·입력·복귀 확인 및 EXECUTIVE 권한 범위 결정.

검수 준비 중 로컬 로그인 주소의 CORS 불일치, 가상 요청 필드명 오류, 전환 전 복원본에 대한 스키마 검사 실패는 검수 환경을 바로잡아 해결했습니다. 운영 제품 결함으로 분류하지 않았습니다. 이번 추가 검수에서는 제품 코드를 변경하거나 새 배포를 하지 않았고, 기존 디자인 변경도 보존했습니다.

## 10. 2026년 4분기부터 관리하도록 범위 변경 — 계획

2026-10-11 사용자는 3분기까지의 TTS를 굳이 저장할 필요가 없으며 분기마다 점수를 체크하므로 올해 4분기와 내년 기록만 필요하다고 설명했습니다. 앞선 전 기간 이관 계획은 아래 계획으로 대체합니다. 이 절은 실행 계획이며 운영 코드·DB·백업 설정을 변경한 결과가 아닙니다.

### 관리 범위와 권장 기준

- 2026년 1~3분기: 신규 이관·운영 점수 집계 대상에서 제외합니다. 3/39주차 휴회 여부와 19주차 점수 차이는 이번 이관의 선행 조건에서 제외합니다. 기존 DB 자료의 실제 삭제는 이 계획 확정이나 범위 축소만으로 실행하지 않습니다.
- 2026년 4분기: 기존 시트의 확정된 주간 총점을 가져오고, 앱 입력으로 이어갑니다. 앞서 읽은 원본 스냅샷의 40·41주차는 양수 점수 84건, 해당 이름 51명, 합계 7,050점입니다. 40주차는 42건/3,345점, 41주차는 42건/3,705점입니다. 실제 이관 직전 최신 원본을 다시 읽고 이 숫자가 바뀌었는지 확인해야 합니다.
- 남은 겹친 점수 차이는 41주차 1건(앱 80점, 시트 100점)입니다. 이전의 2건 중 19주차 차이는 범위 밖입니다. 비교 기준은 여전히 10월 10일 운영 백업이며 이후 앱 수정 가능성을 고려해야 합니다.
- 권장 전환안: 40·41주차는 시트 확정값을 사용하고, 42주차(10/11~10/17)부터 앱을 기록 기준으로 삼습니다. 실제 사용 시작이 늦어지면 마지막 시트 주차와 첫 앱 주차를 함께 옮겨 공백·중복을 막습니다. 점수 충돌 처리와 전환일은 실행 전에 확정합니다.
- 2027년: 1~4분기를 각각 조회·집계합니다. 분기가 바뀌면 새 분기의 합계·순위를 시작하고 완료된 분기의 결과는 조회 가능하게 보존하는 안을 권장합니다. 분기 전환은 이전 기록 삭제나 DB 초기화로 구현하지 않습니다.
- 주간 총점을 나누지 않도록 기존 주차 기준(1~13/14~26/27~39/40~마지막 유효 주)을 유지하는 안을 권장합니다. 이에 따르면 2026년 4분기 첫 주는 40주차(9/27~10/3)이며 시트의 평일 표기는 9/28~10/3입니다. 2027년 1주차는 2026/12/27~2027/1/2입니다. 월 경계와 다를 수 있음을 날짜 범위로 표시하고, 존재하지 않는 53주차를 마지막 주와 중복 계산하지 않도록 검증합니다.

### 코드에서 확인한 보완점

1. `TtsService.getStats`는 시트 점수를 병합하지만 `getQuarterlyScores`는 앱 점수만 계산합니다. 교사용·관리자용의 기간과 점수 출처/충돌 처리 기준을 공통으로 맞춰야 합니다. 시트에만 있는 이름도 누락 여부를 확인합니다.
2. `TTSPage.StatsTab`의 기본 화면은 연간 누적 순위입니다. 분기별 평가 목적에 맞게 현재 분기를 기본으로 보여주고 연도·분기별 합계와 순위를 일관되게 표시합니다.
3. `TtsAdminPage.ScoresTab`은 현재 연도를 고정 사용합니다. 2027년에도 2026년 4분기를 조회할 수 있게 연도 선택을 추가하고 분기 선택과 연결합니다.
4. `importLegacyScores`는 해당 연도의 시트 점수를 전부 교체합니다. 이관 대상 분기/주차를 명시하고 그 범위만 반영하도록 좁혀 다른 분기를 건드리지 않게 해야 합니다. 같은 파일을 재반영해도 중복 점수가 생기지 않도록 검사합니다.
5. 1~3분기 자료를 표시·집계에서 제외하더라도, 연결된 교사회의·기도모임·출석·행사 원본을 TTS 정리 과정에서 함께 삭제하면 안 됩니다. 오래된 TTS 자료 정리가 필요하면 백업과 참조 관계 확인 후 별도 범위를 정합니다.

## 11. PC 정기 백업 — 설정·최초 복원 검증 완료

2026-10-11 사용자가 위 계획 실행을 승인했다. Railway API는 기본 백업 설정을 `Manual backups and backup schedules are only available for Pro workspaces`로 거절했고, 재조회에서도 예약 목록이 비어 있었다. 기본 백업 설정이나 요금제는 변경되지 않았다. 사용자는 현재 요금제를 유지하고 우선 이 PC에 보관하는 방식을 선택했다.

- Windows 작업 `NewaveFlow-EncryptedDatabaseBackup`: 매일 21:00 및 사용자 로그인 시 실행, 같은 날 성공본이 있으면 중복 생성 생략, 놓친 실행 보완, 실패 시 30분 간격 최대 3회 재시도.
- 공개 인증서를 신뢰할 수 있는 SSH 연결로 확보하고 임시 SSH 키는 즉시 해제했다. 이후 백업은 인증서 검증을 유지하는 TLS·읽기 전용 연결을 사용한다.
- `.backups/`를 Git 제외·접근 제한하고 새 백업은 Windows DPAPI로 암호화한다. 접속 비밀번호는 코드·로그·명령 인자에 남기지 않는다.
- 최초 성공본: 한국 시간 19:51, 덤프 원본 크기 189,914바이트. 33개 테이블·2,067개 행을 로컬 별도 DB에 복원해 모든 건수와 내용 해시 일치. 출석·행사·TTS 등 운영 원본 변경 없음.

## 12. 분기 집계·이관 미리보기·복원본 연습 — 로컬 검증 완료

위 10절 계획의 2~4단계를 구현하고 검증했다. 운영 반영 전 결과이며 운영 버전은 `2e4df65` 그대로다.

### 분기와 점수 출처

- 교사용 순위·주차별 표·내 추이와 관리자 점수 현황이 공통 분기 기준을 사용한다. 2026년에는 4분기만 표시하며 2027년부터 1~4분기를 선택한다. 연도 선택으로 이전 결과를 조회할 수 있다.
- 관리자·교사·개인 주간 응답의 시트 우선 기준을 맞췄다. 40·41주차를 이관한 뒤에는 해당 주 전체를 시트 확정 기간으로 취급한다. 빈칸은 앱 점수를 되살리지 않고 기록 없음으로 두며, 명시적 0은 기록으로 보존한다. 기존 앱 답변은 삭제하지 않는다.
- 시트 확정 주차는 개인 체크 수정 대신 확정 총점 또는 기록 없음을 표시한다. 항목별 체크를 총점에서 추정하지 않는다. 42주차 이후에는 기존 앱 입력과 자동 연동을 사용한다.
- 이름이 전체 계정 중 정확히 한 명과 일치할 때만 연결한다. 비활성 동명이인도 검사하며 미가입·동명이인은 별도 시트 기록으로 표시한다. 계정을 자동 생성하지 않는다.
- 주차 시작일은 일요일이다. 2026년 4분기 9/27~12/26, 2027년 1분기 2026/12/27~2027/3/27을 화면에 표시한다. 존재하지 않는 53주차를 52주차와 중복 표시하지 않는다.

### 이관 안전장치

- 기존 연도 전체 교체 API를 2026년 40·41주차 중 선택한 범위만 교체하는 API로 바꿨다. 미리보기 없이 저장할 수 없다.
- 미리보기는 대상 인원·행 수·합계·명시적 0·빈칸·범위 밖 열·교체될 행 수·앱과의 차이·계정 연결 여부를 반환한다. 원본 내용, 해당 범위의 기존 시트 점수 또는 앱 집계가 미리보기 후 바뀌면 409로 거절하고 다시 확인하도록 한다.
- 선택 주차가 모두 빈 표, 중복 이름/주차 열, 소수·음수 점수, 필수 제목 누락, 허용 범위 밖 이관은 저장 전에 거절한다. 저장은 트랜잭션으로 처리한다.
- 관리자 화면에서 미리보기 → 범위·건수·점수 최종 확인 → 반영 순서로 진행한다. 반영 후 교사 통계·분기 점수·관리자 주간 현황·개인 기록 캐시를 갱신한다. 교사 권한의 미리보기/반영 API 호출은 403으로 차단된다.
