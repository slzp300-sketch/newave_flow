# 가입 대기와 이용 정지 관리

일반 교사의 신규 가입 대기와 신고에 따른 이용 정지를 별도 상태로 관리한다. 이용 정지 계정은 가입 승인 API로 다시 활성화할 수 없다.

## 상태와 권한

| 상태 | 저장 상태 | 관리 경로 |
|---|---|---|
| 가입 승인 대기 | `is_active=false`, `is_suspended=false` | ADMIN·PASTOR·EXECUTIVE가 일반 교사 신규 가입 승인 |
| 이용 중 | `is_active=true`, `is_suspended=false` | 기존 교사 권한 관리 |
| 이용 정지 | `is_active=false`, `is_suspended=true`, 정지 시각 | 신고 관리에서 조치, 별도 정지 목록에서 검토 |

- 신고를 통한 정지는 기존 ADMIN·PASTOR·EXECUTIVE 범위를 유지한다. ADMIN·PASTOR 계정을 정지시키는 작업은 ADMIN만 할 수 있다.
- 본인 정지는 금지하며 마지막 활성 ADMIN을 정지하거나 강등할 수 없다.
- 정지 해제는 ADMIN만 할 수 있다. 본인 복구, 사유 누락, 오래된 계정 버전, 삭제 요청이 진행 중인 계정의 복구는 거절한다.
- 복구 시 기존 역할은 유지한다. 기존 ADMIN·PASTOR 합계 최대 2명 규칙을 복구에서도 검사한다. 정지 계정의 역할 변경으로 이 제한을 우회할 수 없다.
- 정지와 복구 때 각각 `auth_version`을 증가시킨다. 복구하더라도 이전 access/refresh token은 유효해지지 않으며 사용자가 다시 로그인해야 한다.
- 가입 승인·정지·복구·권한 변경은 사용자 행을 ID 순으로 잠근 후 최신 상태를 다시 읽는다. 인증 단계에서 읽은 오래된 계정 상태를 잠금 대기 후 재사용하지 않는다. 이 작업은 드문 관리자 작업이므로 해당 작업에만 넓은 잠금 범위를 사용한다.

## 화면과 API

- `/admin/pending-users`: 가입 승인 대기/이용 정지 탭.
- `/admin/pending-users?tab=suspended`: 정지 사유·시각·이력 확인, ADMIN의 복구 사유 입력.
- 기존 교사 권한 화면에서도 활성 계정의 정지·복구 이력을 볼 수 있다.
- `GET /api/admin/users/suspended`: 관리자 전용 정지 목록.
- `GET /api/admin/users/{id}/status-history`: 관리자 전용 최근 100건. 이력은 일반 교사 명단이나 프로필 응답에 포함하지 않는다.
- `PATCH /api/admin/users/{id}/restore`: ADMIN 전용. `{reason, expectedAuthVersion}`가 필요하다.
- 공통 사용자 응답의 `accountStatus`는 `ACTIVE`, `PENDING`, `SUSPENDED` 중 하나이다. 정지 사유는 공통 응답에 포함하지 않는다.

## 이력과 개인정보 삭제

`user_status_events`에는 대상 계정, 수행자, SUSPEND/RESTORE/LEGACY_SUSPEND 구분, 사유, 관련 신고 번호, 시각을 기록한다. 조치 사유에는 필요한 사실만 적고 학생 개인정보를 반복해 적지 않는다.

- 대상 계정 삭제 시 해당 계정의 이력도 삭제한다(`user_id ON DELETE CASCADE`).
- 수행자 계정만 삭제되는 경우 이력은 남기고 수행자 연결을 해제한다(`actor_id ON DELETE SET NULL`).
- 처리 완료 신고의 보관 기간이 끝나 삭제되면 신고 연결을 해제한다(`report_id ON DELETE SET NULL`). 정지·복구 상태 판단에 필요한 별도 계정 조치 이력은 계정 삭제까지 보관한다.
- 실제 계정 삭제 스크립트의 테이블·외래키 허용 목록도 함께 갱신해야 한다. 이력 테이블이 있다는 이유로 알 수 없는 테이블이나 외래키를 자동 허용하지 않는다.

## V012 적용과 기존 기록

`V012__user_suspension.sql`은 이 코드를 배포하기 전에 적용해야 하는 필수 변경이다. V010을 전제로 하며 선택적 Apple 알림용 V011은 요구하지 않는다. 스키마 검사(`ddl-auto=validate`)는 새 열과 이력 테이블을 요구한다.

기존 비활성 계정 중 완료된 SUSPEND_USER 신고가 실제로 남아 있는 계정만 정지 상태로 옮긴다. 최신 해당 신고의 시각과 수행자를 연결하고 원래 사유를 중복 복사하지 않은 LEGACY_SUSPEND 이력을 남긴다. 기존 비밀번호·권한·활성 여부·세션 버전은 변경하지 않는다.

과거 정지 후 이미 활성화된 계정은 다시 정지하지 않는다. 근거가 없거나 보관 기간이 지나 신고가 삭제된 비활성 계정도 임의로 정지라고 추측하지 않는다. 이런 계정은 기존 상태가 유지되므로 가입 승인 전에 실제 신규 가입인지 관리자가 확인해야 한다. 일반 교사가 아닌 근거 불명 비활성 계정은 신규 가입 승인 목록에 넣지 않으며 별도 운영 확인이 필요하다.

새 마이그레이션 적용부터 새 서버 배포까지의 짧은 전환 구간에도 기존 서버는 상태를 변경할 수 있으므로 계정 승인·신고 정지 조작을 피하고, 새 버전 배포 후 비활성 계정과 정지 신고의 불일치 여부를 값 노출 없는 집계로 확인한다.

## 검증

`UserSuspensionHttpTest`는 가입 승인 우회, 권한별 복구, 사유·버전·삭제 요청 검사, 오래된 토큰 재사용, 자기 조치, 마지막 ADMIN 강등, 정지 계정 권한 변경, 오래된 관리자의 상태를 검증한다.

`UserSuspensionMigrationTest`는 명시적으로 지정한 로컬 가상 PostgreSQL에서만 실행한다. V011 없이 적용, 실패 시 전체 복원, 근거가 있는 계정만 backfill, 모호한 기존 상태 보존, 중복 실행 거절, FK 삭제 정책, 운영 스키마 검사까지 검증한다. 테스트 실행 여부와 결과는 작업로그에 별도로 기록한다.
