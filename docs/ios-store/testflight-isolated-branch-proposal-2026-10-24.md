# 운영 유지 조건의 iOS 검수 빌드 경로 제안

상태: 2026-10-24 사용자가 아래 지정 브랜치 임시 허용·서명·TestFlight 업로드 범위를 승인했다. 필수 환경 승인과 동일 커밋 전체 CI를 유지하며, 업로드 후 임시 브랜치 규칙을 제거한다. 완료 여부는 별도 실행 기록으로 확인한다.

## 이유

기존 `ios-testflight` 환경의 허용 브랜치는 main 하나이며, `tools/ios/release-preflight.py`와 `release-readiness.py`도 main과 동일 SHA의 성공 CI를 요구한다. 현재 수정은 `codex/ios-review-clarity`에 있고 main은 운영 웹·서버와 연결될 수 있다. 기존 서명 명령을 이 브랜치에 실행하면 차단된다.

## 승인받을 구체적 범위

1. 기존 `ios-testflight` 환경에 **정확히 `codex/ios-review-clarity` 한 브랜치만** 추가 허용한다. 와일드카드·다른 브랜치는 허용하지 않는다. 기존 필수 검토자와 승인 대기 절차는 그대로 유지한다.
2. 서명 도구는 main 또는 위 한 브랜치만 허용하도록 보완한다. 선택 브랜치 현재 HEAD와 입력 SHA 일치, 같은 SHA의 전체 회귀·PostgreSQL·iOS CI 성공, 서명 직전 재검사를 유지한다. CI 실패/누락, SHA 변경, 다른 브랜치는 계속 차단한다. 변경한 검증 규칙 자체도 테스트한다.
3. 수정 브랜치만 원격 저장소에 저장한다. 원격 main merge/push는 하지 않는다. 브랜치 push에 웹/서버 배포가 연결돼 있지 않은지 먼저 확인하고, 연결돼 있다면 push를 멈춘다. Vercel에서 이 브랜치의 Git 자동 배포를 비활성으로 명시한 설정을 후보 코드에 포함한다.
4. 현재 자격증명·Apple 로그인 권한을 재사용한다. 새 키 발급, 인증서/프로파일 재발급, 푸시 활성화는 하지 않는다. 비밀값은 출력하거나 artifact로 보관하지 않는다.
5. 새 미사용 빌드 번호로 서명해 TestFlight에 올리고 기존 운영자 검수 기기에서만 확인한다. 정식 App Review 재제출, 공개 출시, 외부 테스터 이메일 발송은 별도 단계다.
6. 서명/업로드 완료 후 새로 추가한 브랜치 허용 규칙을 제거하고 main만 남았는지 확인한다. 기존 승인 규칙은 변경하지 않는다.

## 영향과 한계

- 허용 기간에 지정 브랜치가 기존 승인 절차를 거쳐 서명·업로드 비밀값을 사용할 수 있게 된다. 이 권한 확대에 대한 명시 승인이 필요하다.
- 운영 앱·웹·서버 및 main은 변경하지 않는 경로다. 현재 가상 서버의 초기화 방지 패치는 별도 서버 반영 전까지 실제로 동작하지 않는다. 신규 iOS 빌드 검사 결과와 미반영 서버 수정 결과를 구분한다.
- iPhone 17 / iOS 26.6.2 / TestFlight 설치 완료는 사용자 제공 정보다. 새 빌드를 생성하기 전에는 기존 앱으로 이번 수정의 실기기 통과 여부를 판단할 수 없다.
- 이 계획의 승인 후에도 CI 또는 Apple 처리 실패가 있으면 원인을 해결하고 결과를 확인한다. 승인만으로 업로드 완료로 기록하지 않는다.
