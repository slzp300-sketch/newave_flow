## NF-011 홈 메뉴 통합 · 사전 구현 (2026-10-19)

- 홈은 체크·참여 5개, 기록·일정 3개, 학생·반 2개의 전체 기능 메뉴로 통합했다. 큰 TTS 카드·주간 일정 미리보기·이번 주 할 일은 홈에서 제거하고 기능 페이지는 유지한다.
- 하단은 홈·일정·내 정보 3개다. `/menu`, `/checklist`는 홈으로 연결하며 기능별 상위 화면·선택 탭·안전한 이용의 내 정보 복귀를 맞췄다.
- 미체크/미제출/미응답/미확인은 빨간 점과 짧은 문구로 표시한다. 반 공동 제출, 불참 응답, 공개 회의록 확인을 구분한다. 전도 배정은 중립색, 새 일정은 파란색이다. 오류·오프라인은 확인 필요이며 완료나 미제출로 단정하지 않는다.
- TTS는 이번 주의 오늘 및 지난 수정 가능 날짜만 확인한다. 미래 날짜·마감 분기·이관 기록·자동 연동 항목은 제외한다. 주 1회 직접 체크 항목은 실제 참여일 필드가 없어 서버의 토요일 `attendanceDate`가 도래한 때부터 표시한다. 제목으로 참여 날짜를 추측하지 않으며 분기 귀속도 토요일 기준을 유지한다.
- 관리 메뉴는 기존 ADMIN/PASTOR/EXECUTIVE 권한을 유지하며 신고·사진 검토는 마지막에 둔다. 기존 관리 요약·편집 가능한 바로가기는 관리자 화면으로 이동했고 원래 해당 요약을 보던 ADMIN/PASTOR만 접근한다. 개인 미체크와 관리 대상자의 상태는 섞지 않는다.
- 그리드는 기본 3열, 359px 이하와 큰 글씨 모드에서는 2열이다. 기존 새로고침·애니메이션·불참 색상·통계 보기·분기 잠금·내 정보 계정 연결·푸시 준비 소스를 유지한다. 회의록 확인 성공 시 홈의 주간 상태 캐시도 갱신한다.
- 가상 응답만 사용하는 로컬 화면에서 교사/관리자/목사/임원 메뉴, 불참 저장 후 홈 완료 표시, 완료·미확인·오류·오프라인, 작은 화면과 큰 글씨를 확인했다. 실제 운영 API·개인 명단은 사용하지 않았다. 네이티브 재검사 결과는 이후 검사 기록에 추가한다.

### iOS 사전 통합·화면 검수 완료 (2026-10-19 12:24 KST)

[9865231의 macOS 검사](https://github.com/slzp300-sketch/newave_flow/actions/runs/39193334757)는 전체 성공했다. Release 컴파일·번들/서명 검사, 웹 자동 검사 130개, 네이티브 8개, iPhone SE 3세대와 iPad 호환 모드의 실제 Release 로그인 화면 OCR 검사를 통과했다. 최종 캡처도 직접 확인했으며 브랜드·아이디/비밀번호·로그인 버튼이 정상 표시된다. 로컬 검증 도구 합성 테스트는 76개 통과했다. GitHub 증빙은 5일 보관이며 로컬 `.verification/ios-ci-39193334757`에도 다운로드했다.

Intel WebKit GPU 실패를 피해 표준 Apple Silicon 호스트를 사용하고, iPhone은 Debug 통합 테스트 이후의 상태를 초기화한 뒤 Release 앱을 설치하도록 검증 환경을 분리했다. 이 옵션은 GitHub-hosted 일회용 환경에서만 허용하며 개인 PC·self-hosted 환경에서는 실행 전에 거절한다. iPhone 설치 36.86초, 전체 246.19초 / iPad 전체 239.71초로 기존 기기당 총 510초 한도 안에서 성공했다. 캡처/OCR 각 60초 및 합산 150초, 설치 180초 한도는 총 기기 시간에 맞춰 축소하며 실패·빈 화면·오래된 이미지의 성공 처리는 허용하지 않는다. 초기화가 지연의 유일한 원인이었다고 단정하지 않으며 이전 실패 기록도 Notion에 보존한다.

이번 추가 변경은 CI와 검증 도구 및 기록뿐이다. 운영 main·서버·DB·현재 App Store 심사와 TestFlight 빌드는 변경하지 않았다. CI는 배포용 서명/Apple 로그인 활성화 설정 없이 검사하므로 실제 Apple 신규가입·중계 이메일·삭제·철회 또는 실제 APNs/FCM 수신 검수를 대체하지 않는다. 개선된 로그인 후 업무 화면의 기존 9개 웹 검수와 이번 네이티브 초기 화면 검수도 구분한다.

### 실제 반영 단계

1. 현재 심사를 유지하고 출시 결과를 확인한다. 이 브랜치는 Vercel 자동 배포 대상에서 제외했으며 main·Railway 운영은 건드리지 않는다.
2. 변경분 검토 후 운영 백업/복원 검증과 V015→V016 적용을 승인받아 실행한다. 이번에는 가상 DB만 검사했다. 새 서버보다 스키마를 먼저 적용해야 한다.
3. 백엔드→웹/새 네이티브 앱 순서로 반영한다. 서버 플래그 `NOTIFICATIONS_ENABLED`, `PUSH_ENABLED`, `PUSH_IOS_ENABLED`, `PUSH_ANDROID_ENABLED` 및 네이티브 `VITE_NATIVE_PUSH_ENABLED`는 모두 기본 false다. 새 앱의 푸시 UI도 빌드 플래그가 false이면 숨긴다.
4. 푸시는 APNs 권한·키·production 서명 프로파일, Android Firebase 프로젝트 설정·전송 권한을 별도로 연결한다. iOS 수동 빌드의 `push_notifications` 입력이 true일 때만 푸시 entitlement를 요청하며 실제 프로파일·서명 결과를 검사한다.
5. 개인정보 안내 초안의 시행일/제공자 조건과 두 스토어 신고를 확정한다. 내 정보의 선택 안내·OS 권한 요청을 포함해 검수 기기에서 실제 수신·잠금 화면·포그라운드·탭·로그아웃·계정 전환을 확인한다.
6. 앱 버전·빌드 번호를 올려 TestFlight/Play 검수 후 업데이트를 제출한다. 이 작업에서 운영 공개·새 업로드·심사 취소·재제출은 하지 않았다.

## 호환성과 운영 한계

- 기존 앱도 마감된 TTS 수정은 서버가 거절한다. 다만 기존 1.0.0(3)은 분기를 13주씩 직접 합산하므로 새 달력 분기 필드를 읽지 않는다. 분기 경계가 있는 주의 정확한 통계는 새 앱으로 업데이트해야 한다. 새 서버를 반영한 뒤에는 교사들에게 업데이트를 안내하고, 오래된 앱의 분기 통계와 새 관리자 합계가 다를 수 있음을 명시한다.
- 서버가 오전 9시에 중단돼 있으면 해당 정기 알림을 자동 소급 생성하지 않는다. 전송 성공 직후 저장 전 서버 장애까지 포함한 외부 푸시 정확히 한 번 전달은 보장하지 않는다. 앱 내 중복 키·전송 행 잠금·공급자 collapse/tag로 중복 영향을 줄인다.
- 가짜 응답/웹 검수만으로 실제 푸시 도착·Apple 심사 통과·출시 시점을 확정하지 않는다. 소스 사전 준비와 외부 활성화·배포를 구분한다.
