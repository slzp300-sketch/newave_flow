# 신고·이용수칙 기능 반영 절차

콘텐츠 작성 전에 이용수칙을 직접 확인하고, 콘텐츠·사용자 신고와 관리자 처리 결과를 앱 안에서 제공한다. 기존 학생·교사 자료를 동의 완료로 바꾸지 않는다. 개인정보 관련 별도 동의 수집은 이 기능과 별도다.

## 반영 순서

1. 현재 코드를 검사하고 최신 운영 백업을 접근 제한 로컬 DB에 복원한다. 값·건수/해시 일치, 강제 실패 롤백, 중복 실행 거절, prod/validate 서버 기동을 확인한다. 실제 자료나 접속값을 Git/작업로그로 전송하지 않는다.
2. `backend/db/migrations/V008__community_safety.sql`만 한 번 적용한다. 동의 기록과 신고 테이블을 추가하며 기존 업무 행은 바꾸지 않는다. V001~V007을 재실행하지 않는다. 기존 테이블의 적용 전후 보존을 확인한다.
3. 새 서버는 두 테이블을 기대하므로 SQL보다 main 자동 배포가 먼저 시작되지 않게 한다. 새 백엔드·웹을 반영하고 운영에서는 읽기만 확인한다.
4. 별도 심사 서비스는 `tools/review/prepare-deployment.ps1`로 새 허용 목록 묶음을 준비해 해당 서비스에만 업로드한다. 실제 명단·운영 연결값·키·암호를 포함하지 않는다. main 푸시만으로 심사 서비스가 갱신되지 않는다.
5. 가상 교사·관리자 계정으로 동의 → 신고 → 권한 차단 → 관리자 결과 → 신고자의 안내 표시를 검사한다. 실제 이용자의 승인·콘텐츠·학생 자료를 시험 수정하지 않는다.
6. Android 후보는 운영 API·정상 release 설정·기존 인증서를 확인한다. 이미 업로드한 versionCode를 바뀐 AAB에 재사용하지 않는다. 실제 폰/Play 설치 검수는 브라우저·린트 검사와 구분해 기록한다.

## 운영 기준

- 일반 교사는 본인 신고만 보며 관리자는 업무에 필요한 범위로 검토한다. 입력에 비밀번호·인증번호 등 불필요한 정보를 넣지 않도록 안내한다.
- 회의록 숨김은 원문을 보존한다. 사용자 이용 제한은 기존 세션도 종료한다. 다른 문서의 실제 조치는 기존 관리 화면에서 수행하고 신고에는 결과를 기록한다.
- 구형 앱은 동의 없이 작성할 때 428을 받는다. 같은 계정으로 웹의 전체 메뉴에서 이용수칙을 확인하면 서버 기록이 공유된다. 설치된 앱의 업데이트와 안내를 함께 제공한다.
- `backend/db/privacy/purge-resolved-content-reports.sql`은 처리 완료/위반 없음으로 종료한 신고 중 90일 경과분을 정리한다. 미해결 신고·동의 기록·원래 업무 문서는 지우지 않는다. 운영자가 별도 보관기간 점검 절차에서 실행한다.
- 계정 삭제는 검토된 요청마다 기존 개인정보 삭제 절차를 따른다. 새 동의·신고 연결도 처리하며 공동 업무 기록은 보존한다.

## 실패 시

SQL 실패는 한 트랜잭션으로 롤백한다. 새 테이블만 추가한 단계에서는 이전 코드가 이를 무시하므로 코드 복귀 때 기존 자료를 과거 백업으로 덮어쓰지 않는다. 새 버전에서 신고·동의 기록이 생겼다면 보존하고 복구 계획에 포함한다. 스키마 오류를 자동 update로 우회하지 않는다.
