2026-10-12 사용자가 승인한 범위: 개인 계정·연락처·프로필·TTS는 삭제하고, 공동 반 보고서는 개인을 식별할 수 없게 처리해 보존한다. 공개 접수 주소는 slzp300@gmail.com이다.

앱에서 현재 비밀번호로 본인을 다시 확인한 정식 접수 또는 이메일 본인 확인을 거쳐 담당자가 실행하는 절차다. 앱 접수는 개인정보의 실제 삭제가 끝났다는 뜻이 아니며, 기존 메일 작성 버튼 자체도 접수/삭제 완료를 뜻하지 않는다. 운영 DB에서 실제 삭제를 시험하지 않으며, 실제 계정 삭제는 해당 이용자의 확인된 요청이 있는 경우에만 실행한다.

## 앱 안에서 접수하고 결과 확인하기

- `POST /api/account-deletion`은 로그인한 본인의 현재 비밀번호와 `confirmed: true`만 받아 요청을 접수한다. 대상 사용자 ID를 입력받지 않는다. 현재 계정 버전을 다시 확인하고 사용자 행을 잠가 반복 제출은 같은 요청으로 처리한다.
- 접수가 성공하면 로그인 방식과 관계없이 기존 세션을 무효화한다. 앱은 응답의 접수증을 먼저 보관하고 로그아웃한 뒤 상태를 보여준다. 이메일·비밀번호로 다시 로그인하면 처리 중 상태와 새 접수증을 확인할 수 있다.
- Apple 연결 계정은 접수 전 Apple의 권한 철회가 성공해야 한다. 철회 시각을 기록하고 암호화 토큰은 제거하며, 삭제가 완료되기 전에도 Apple 로그인·새 연결은 차단한다. 이메일·비밀번호 로그인은 실제 삭제 완료 전까지 사용할 수 있다. 모든 Apple 가입자는 앱 비밀번호를 설정한다.
- 마지막 관리자도 접수할 수 있지만 운영 권한 인계가 필요하다고 안내한다. 실제 삭제 SQL의 마지막 관리자 보호는 유지한다. 자동으로 다른 사람을 관리자로 바꾸거나 공동 자료를 지우지 않는다.
- `GET /api/account-deletion`은 본인의 접수 상태만 반환한다. 로그인 없이 결과를 확인할 때는 `POST /api/auth/account-deletion/status`의 본문에 접수증 토큰을 전달한다. 토큰은 URL에 넣지 않는다. 상태 응답에는 이메일·이름·사용자 ID·검토 내용이 없다.
- 접수증은 32바이트 무작위 토큰이며 DB에는 SHA-256 해시만 보관한다. 비밀번호를 재확인한 반복 접수는 접수번호·접수 시각·7일 목표기한을 유지하고 새 접수증만 발급한다. 이전 접수증은 무효가 된다. 비밀번호·접수증 원문을 Git, 채팅, 노션, 서버 로그에 남기지 않는다.
- 담당자는 `node tools/privacy/account-deletion.cjs requests`로 미완료 접수번호·내부 ID·기한을 읽기 전용으로 확인한다. `plan <userId>`는 앱 접수번호와 계정 생성 시각을 대조해 같은 번호의 보호된 검토안을 만든다. 앱 접수만으로 기존 인계·동명이인·자유 텍스트·외부 사본 검토를 생략하지 않는다.
- 실제 삭제 SQL이 사용자 행과 개인 자료를 제거하는 같은 트랜잭션에서 접수 상태를 `COMPLETED`로 바꾸고 사용자 ID·계정 생성 시각 연결을 지운다. 어떤 검증이 실패하면 완료 표시도 함께 롤백된다. 삭제 후 기존 JWT와 갱신 토큰은 사용자 행이 없어 사용할 수 없다.
- 익명 완료 접수증은 완료 후 30일 동안 조회할 수 있고 이후 서버 정리 작업으로 제거한다. 대기 요청은 기한이 지났다는 이유로 제거하지 않는다. 백업의 삭제 재적용을 위한 암호화 이력은 아래 별도 절차를 따른다.

이 기능에는 `V010__account_deletion_requests.sql`이 필요하다. Apple 연동이 있는 계정은 `V009`의 Apple 연결/흐름 스키마와 권한 철회 기능도 함께 적용한다. 이메일로 접수한 Apple 계정 역시 실제 삭제 전에 앱의 본인 확인과 Apple 권한 철회를 완료해야 하며, 철회 기록 없이 SQL로 우회하지 않는다.

Apple 서버 알림용 V011은 별도 활성화 단계에서 적용한다. 최신 삭제 SQL은 V011이 없는 기존 운영 구조에서도 동작한다. V011이 있으면 대상 사용자에게 연결된 `apple_notification_subjects`와 해당 `apple_notification_receipts`만 삭제하고 다른 계정·미연결 상태는 보존한다. 두 테이블 중 하나만 있거나 미검토 외래키가 추가된 경우 삭제를 중단한다. 정해진 SHA-256 열은 형식 검증 후 원문 이름 검색에서 제외하며, 새로운 텍스트 열은 계속 검사한다. Apple 알림만으로 앱 계정 삭제를 접수하거나 실행하지 않는다.

## 접수와 본인 확인

1. 앱 접수는 서버가 현재 비밀번호 재인증을 완료했는지 확인한 접수번호를 사용한다. 이메일 접수는 가입 이메일에서 요청했는지 확인한다. 운영자가 비밀번호·신분증 사진을 받지 않는다.
2. 다른 주소에서 온 경우 계정 소유자임을 별도 확인한다. 확인 전에는 계정 존재 여부나 개인정보를 답변에 포함하지 않는다.
3. 대상 계정의 내부 ID와 요청 범위를 확인하고 개인 정보를 포함하지 않는 접수 번호로 처리 이력을 남긴다.
4. 담당 반 이전과 마지막 관리자 계정 여부를 확인한다. 서비스 관리자가 사라지는 경우 담당자 이전을 먼저 조정한다.

- `event_attendances`: 교사 개인 참석 자료. `event_student_attendances`의 학생 참석 결과는 공동 기록이므로 제출자 식별 정보와 구분한다.

- 회의록·공동 보고서·메모 등 자유기술 문서: 이름·전화번호 등을 사람이 확인한다. 같은 이름을 일괄 치환해 다른 사람의 내용을 바꾸지 않는다.
- 완료 작업 기록 및 별도 과거 원본·스프레드시트·암호화 백업도 보관 책임자와 처리 범위를 확인한다.

## 실제 요청 한 건의 실행 순서

1. 접수 번호를 발급하고 본인 확인, 담당 반 인계, 외부 사본(시트·메신저·문서·메일 포함)을 검토한다. 현재 사용자 ID와 계정 생성시각을 대조한다. 마지막 관리자는 먼저 운영 권한을 인계한다.
2. `node tools/privacy/account-deletion.cjs plan <userId>`로 읽기 전용 조사한다. 검수안은 접근이 제한된 `.backups/privacy/<요청번호>.review.json`에만 생성한다. 채팅·Git·노션에 원문을 붙이지 않는다.
3. `reviewCandidates`는 이름·이메일·전화번호가 남은 필드의 ID/해시 목록이다. 과거 이름·연락처도 `identifiers`에 추가한다. 자동 검색이 찾지 못하는 별명·이미지·첨부·문맥상의 식별 정보는 별도 사람이 확인한다.
4. `legacyDecisions`의 각 행을 참/거짓으로 확정하고, `redactions`에는 `table`, `column`, `id`, `beforeMd5`, `replacement`를 지정한다. 다른 사람의 동일 이름을 보존할 때만 `exceptions`에 정확한 행/필드/해시와 10자 이상의 설명을 넣는다. 검토가 끝난 네 가지 확인 항목만 `true`로 바꾼다.
5. 최신 암호화 백업을 별도 `newave_privacy_...` 로컬 DB에 복원하고 V004를 적용한다. `PRIVACY_REHEARSAL_DATABASE` 환경변수를 이 이름으로 지정한 뒤 `node tools/privacy/account-deletion.cjs rehearse <보호된 검수안 경로>`를 실행한다. **rehearse는 로컬 DB만 허용하며 전부 롤백한다.**
6. 공동 자료·다른 사람 자료 보존 및 예외 항목을 재확인한다. 유지보수 시간에 백엔드와 작업을 정지하고 진행 중 요청이 끝난 것을 확인한다. 이전 요청이 삭제 후 이름/기록을 다시 쓰지 못하게 하기 위한 필수 단계다. 해당 이용자의 실제 요청을 처리할 권한과 범위를 확인한 담당자만 `node tools/privacy/account-deletion.cjs execute <보호된 검수안 경로> <정확한 요청번호> --maintenance-confirmed`를 실행한다. 이번 개발 검수에서는 이 명령을 운영 계정에 실행하지 않았다.
7. 암호화된 `.pending.dpapi` 삭제 의도를 디스크에 기록/동기화한 후 DB를 커밋하고 `.done.dpapi`로 확정한다. 커밋/파일 확정 실패로 pending이 남으면 완료로 안내하지 않는다. 요청과 DB의 현재 상태를 확인해 담당자가 복구한다. pending을 무조건 지우거나 같은 요청을 다시 실행하지 않는다.
8. 정상 완료 후 평문 검수안은 제거되고 암호화 이력만 남는다. 기존 토큰·재승인 차단, 개인 자료 제거, 공동 집계 보존을 확인한다. 백업과 외부 사본의 잔여 처리 사항을 포함해 신청자에게 결과를 알린다. 실제 메일 발송은 별도 사용자 지시가 있어야 한다.

## 복원·이력 보관

백업 원본 건수/해시 대조 후 `replayLedger`로 확정된 삭제를 복원 DB에 재적용한다. 미완료 의도나 복원 데이터와 검수안의 불일치가 있으면 중단하고 복원본을 운영에 연결하지 않는다. 오래된 DB에 V004가 없으면 먼저 필요한 스키마를 적용하고 새로 검수한다.

삭제 이력에는 요청 ID·계정 ID·생성시각·식별 문자열·검토안이 포함되므로 개인정보다. DPAPI로 암호화하고 담당자만 접근한다. 관련 백업/외부 사본이 모두 만료·삭제됐는지 확인한 뒤 담당자가 이력도 제거한다. pending·미완료 요청을 나이만 보고 자동 제거하지 않는다. 이력 손실 또는 다른 PC로 이전 시에는 복원 서비스를 열기 전에 담당자의 별도 대조가 필요하다.

## 점검 결과

가상 PostgreSQL 검수에서 개인 계정/TTS/교사 행사 기록 제거, 학생·공동 보고서 보존, 반 집계 유지, 과거 보고서 텍스트 정리, 검토 미완료/대상 변경/알 수 없는 FK/마지막 관리자 차단과 전체 롤백을 확인했다. 백업 만료 및 삭제 의도 기록·재적용의 Node 검사도 통과했다. 상세 최종 결과는 노션 작업로그에 기록한다.
