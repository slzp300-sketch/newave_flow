## 앱 안에서 접수하고 결과 확인하기

- `POST /api/account-deletion`은 로그인한 본인에 대해 `confirmed: true`와 현재 비밀번호 또는 Apple 일회성 재인증 증명(`appleFlowId`, `appleTicket`, `appleVerifier`)을 받아 요청을 접수한다. Apple 전용 계정은 `/api/users/me/apple/deletion/start`와 새 Apple 시스템 인증으로 삭제 전용 증명을 얻는다. 증명은 계정·세션·Apple 식별자에 묶이고 한 번만 소비하며 기기에 따로 저장하지 않는다. 인증 취소 시 접수 요청을 보내지 않는다. 대상 사용자 ID를 입력받지 않고 현재 계정 버전·활성 상태를 다시 확인한다.
- 배포 전 후속 경로 `POST /api/auth/account-deletion`은 이메일·현재 비밀번호 또는 새 Apple 삭제 증명 중 하나로 본인을 확인한다. Apple 전용 계정은 로그인 세션 없이 `/api/auth/apple/deletion/start`에서 삭제 전용 인증을 시작하고 서버가 검증한 Apple 식별자로 기존 소유자를 결정한다. 승인 대기·정지 상태를 해제하거나 일반 로그인 토큰·새 앱 계정을 발급하지 않는다. 클라이언트가 대상 사용자 ID를 정할 수 없고, 잘못된 이메일·비밀번호는 계정 존재 여부를 나누어 알려주지 않는다.
- 접수가 성공하면 로그인 방식과 관계없이 기존 세션을 무효화한다. 앱은 응답의 접수증을 먼저 보관하고 로그아웃한 뒤 상태를 보여준다. 이메일·비밀번호로 다시 로그인하면 처리 중 상태와 새 접수증을 확인할 수 있다.
- Apple 연결 계정은 접수 전 Apple의 권한 철회가 성공해야 한다. 철회 시각을 기록하고 암호화 토큰은 제거하며, 삭제가 완료되기 전에도 Apple 로그인·새 연결은 차단한다. 기존 앱 비밀번호가 있는 계정은 실제 삭제 완료 전까지 이메일·비밀번호로 접수 상태를 확인할 수 있다. Apple 신규 가입은 별도 앱 비밀번호를 요구하거나 생성하지 않으므로, Apple 전용 계정은 철회 후 접수증으로 상태를 확인한다.
- 마지막 관리자도 접수할 수 있지만 운영 권한 인계가 필요하다고 안내한다. 실제 삭제 SQL의 마지막 관리자 보호는 유지한다. 자동으로 다른 사람을 관리자로 바꾸거나 공동 자료를 지우지 않는다.
- `GET /api/account-deletion`은 본인의 접수 상태만 반환한다. 로그인 없이 결과를 확인할 때는 `POST /api/auth/account-deletion/status`의 본문에 접수증 토큰을 전달한다. 토큰은 URL에 넣지 않는다. 상태 응답에는 이메일·이름·사용자 ID·검토 내용이 없다.
- 접수증은 32바이트 무작위 토큰이며 DB에는 SHA-256 해시만 보관한다. 비밀번호를 재확인한 반복 접수는 접수번호·접수 시각·7일 목표기한을 유지하고 새 접수증만 발급한다. 이전 접수증은 무효가 된다. 비밀번호·접수증 원문을 Git, 채팅, 노션, 서버 로그에 남기지 않는다.
- 담당자는 `node tools/privacy/account-deletion.cjs requests`로 미완료 접수번호·내부 ID·기한을 읽기 전용으로 확인한다. `plan <userId>`는 앱 접수번호와 계정 생성 시각을 대조해 같은 번호의 보호된 검토안을 만든다. 앱 접수만으로 기존 인계·동명이인·자유 텍스트·외부 사본 검토를 생략하지 않는다.
- 실제 삭제 SQL이 사용자 행과 개인 자료를 제거하는 같은 트랜잭션에서 접수 상태를 `COMPLETED`로 바꾸고 사용자 ID·계정 생성 시각 연결을 지운다. 어떤 검증이 실패하면 완료 표시도 함께 롤백된다. 삭제 후 기존 JWT와 갱신 토큰은 사용자 행이 없어 사용할 수 없다.
- 익명 완료 접수증은 완료 후 30일 동안 조회할 수 있고 이후 서버 정리 작업으로 제거한다. 대기 요청은 기한이 지났다는 이유로 제거하지 않는다. 백업의 삭제 재적용을 위한 암호화 이력은 아래 별도 절차를 따른다.

이 기능에는 `V010__account_deletion_requests.sql`이 필요하다. Apple 연동에는 `V009`의 연결/흐름 스키마, 비밀번호 없는 가입·삭제 재인증에는 `V014__apple_passwordless.sql`이 필요하다. V014 운영 적용은 2026-10-16 완료했다. 이메일로 문의한 Apple 계정 역시 실제 삭제 전에 본인 확인과 Apple 권한 철회를 완료해야 하며, 철회 기록 없이 SQL로 우회하지 않는다.

Apple 서버 알림용 V011도 2026-10-16 운영에 적용했다. 과거 백업 복원을 위해 삭제 SQL은 V011이 없는 구조도 처리한다. V011이 있으면 대상 사용자에게 연결된 `apple_notification_subjects`와 해당 `apple_notification_receipts`만 삭제하고 다른 계정·미연결 상태는 보존한다. 두 테이블 중 하나만 있거나 미검토 외래키가 추가된 경우 삭제를 중단한다. 정해진 SHA-256 열은 형식 검증 후 원문 이름 검색에서 제외하며, 새로운 텍스트 열은 계속 검사한다. Apple 알림만으로 앱 계정 삭제를 접수하거나 실행하지 않는다.

## 접수와 본인 확인

1. 앱 접수는 서버가 현재 비밀번호 또는 새 Apple 인증의 일회성 증명을 확인한 접수번호를 사용한다. 이메일 문의는 가입 이메일과 계정 소유 관계를 확인하되, 비밀번호 없는 Apple 계정에 새 앱 비밀번호 입력을 요구하지 않는다. 운영자가 비밀번호·신분증 사진을 받지 않는다.
2. 다른 주소에서 온 경우 계정 소유자임을 별도 확인한다. 확인 전에는 계정 존재 여부나 개인정보를 답변에 포함하지 않는다.
3. 대상 계정의 내부 ID와 요청 범위를 확인하고 개인 정보를 포함하지 않는 접수 번호로 처리 이력을 남긴다.
4. 담당 반 이전과 마지막 관리자 계정 여부를 확인한다. 서비스 관리자가 사라지는 경우 담당자 이전을 먼저 조정한다.

## 삭제·익명화 대상 조사

- `users`: 이름·이메일·전화번호·생일·프로필 사진·직분·학년·비밀번호 및 세션 무효화. 비활성화만으로 삭제를 완료하지 않는다.
- `apple_accounts`, `apple_auth_flows`: 본인 확인·권한 철회를 마친 연결과 인증 흐름 제거. 선택적 V011이 있으면 해당 계정의 알림 상태·수신 해시도 제거한다. 해시는 이름 검색 결과가 아니라 사용자 소유 관계로 삭제 대상을 판단한다.
- `tts_data_entry`, `tts_answers`: 개인 영성 기록 제거. `tts_legacy_score`는 이름 기준이므로 동일 이름의 다른 사람 자료를 지우지 않도록 별도 식별·대조한다.
- `teacher_classes`, `user_tags`, `event_reads`, `notifications`, `meeting_minute_confirms`, `checklist_records`, `prayer_votes`, `meeting_attendances`, 전도 조/일정 배정: 개인 연결과 활동 자료 처리.
- `event_participants`: 과거 교사 명단 스냅샷의 이름·학년·반 정보. 현재 사용자 이름만 바꿔서는 이 자료가 지워지지 않는다.
- `event_attendances`: 교사 개인 참석 자료. `event_student_attendances`의 학생 참석 결과는 공동 기록이므로 제출자 식별 정보와 구분한다.
- `student_memos`: 학생별·교사별로 저장된 개인 기도제목·관찰 메모는 요청자의 `teacher_id`에 속한 행을 삭제한다. 다른 교사의 메모와 학생 원장은 보존한다. 과거에 작성자 참조가 이미 비워진 메모는 자동 소유 추정 없이 공동 자유문 검토에 포함한다.
- `attendances`, `daily_reports`, `deactivation_requests`: 교사 외래키와 공동 내용의 보존 범위를 분리한다. 학생·출석 상태·집계 행은 보존하며 요청자 개인 작성 내용은 검토한 필드만 삭제/부분 삭제한다. 특히 `daily_reports.teacher_id`는 마지막 수정자라 본문 전체의 소유자로 간주하지 않는다.
- `daily_reports_before_class_merge`: 운영 전환 당시 보존한 원본에도 제출자 ID·자유기술 이름 등이 남을 수 있다.
- 회의록·행사·공동 보고서 등 자유기술 문서: 작성자 열이나 이름·전화번호가 없어도 본문 소유권을 사람이 확인한다. 같은 이름을 일괄 치환해 다른 사람의 내용을 바꾸지 않는다. 제목·링크·과거 보고서·운영자의 검토 메모·공동 양식 문구도 검토 범위에 포함한다.
- 완료 작업 기록 및 별도 과거 원본·스프레드시트·암호화 백업도 보관 책임자와 처리 범위를 확인한다.

## 처리와 검증

1. 접근 제한된 최신 복원본에 가상 삭제 대상과 공동 기록을 만들고 트랜잭션 삭제 절차를 검증한다.
2. 개인 정보·TTS 제거, 과거 명단 익명화, 다른 교사·학생·공동 집계 보존, 기존 토큰 차단, 재승인으로 되살릴 수 없는 상태를 확인한다.
3. 실패 시 전체 롤백되는지 확인한 뒤에만 확인된 실제 요청을 처리한다.
4. 백업을 복구할 때 이미 처리한 삭제 대상이 되살아나지 않도록 삭제 완료 이력을 적용한다.
5. 신청자에게 결과와 별도 보관이 있다면 근거·항목·기한을 안내한다. 발송은 요청을 처리하는 운영자가 진행한다.

- `tools/privacy/account-deletion.cjs`: 운영자 전용 CLI. 웹에는 신청·상태 API만 제공하며 실제 삭제 실행 API를 개방하지 않는다. 명시적으로 검토·확인한 요청 한 건만 실행한다.
- `backend/db/privacy/request-tables.sql`, `delete-account.sql`: 트랜잭션 단위 삭제. 검토 불충분, 계정 생성시각 불일치, 마지막 관리자, 검토 이후 내용 변경, 알 수 없는 외래키, 잔여 식별 텍스트가 있으면 전체 롤백한다.
- `backend/db/privacy/content-scope.sql`, `tools/privacy/content-review.cjs`: 공유 자유문 검토 범위를 코드로 고정하고, 비어 있지 않은 모든 대상 필드의 행/해시를 수집한다. 고정 상태값·형식값과 별도 검수하는 이미지 필드를 제외한 새 자유문 열도 자동으로 검토 대상에 들어간다. 검토안은 본문을 출력하지 않으며, 담당자는 보호된 원본과 작성 경위를 따로 대조한다.
- 과거 이름만 있는 TTS는 각 행의 소유자를 사람이 결정한다. 동명이인 자료에 ‘삭제 안 함’을 정할 때에는 남겨야 하는 정확한 필드/행/내용 해시/사유도 검토 예외에 남긴다. 이름 전체 일괄 삭제·치환은 하지 않는다.
- 현재 SQL은 대상 교사의 개인 학생 메모·교사 행사 명단 스냅샷·개인 행사 응답을 삭제한다. 공동 출석·보고·제적 요청·학생 행사 참석은 행·집계와 교사 참조를 분리한다. 본문은 아래 명시적 소유권 결정에 따라 정확한 필드만 비우거나 부분 교체하며, 마지막 수정자라는 이유로 전체 문서를 삭제하지 않는다.

## 실제 요청 한 건의 실행 순서

1. 접수 번호를 발급하고 본인 확인, 담당 반 인계, 외부 사본(시트·메신저·문서·메일 포함)을 검토한다. 현재 사용자 ID와 계정 생성시각을 대조한다. 마지막 관리자는 먼저 운영 권한을 인계한다.
2. 예약 백업과 동일한 `NEWAVE_BACKUP_DIRECTORY`를 지정한다. 이 PC에서는 `$env:NEWAVE_BACKUP_DIRECTORY = Join-Path $env:LOCALAPPDATA 'NewaveFlow\Backups\automatic\.backups'`다. `node tools/privacy/account-deletion.cjs plan <userId>`로 읽기 전용 조사한다. 검수안은 지정한 보호 폴더 아래 `privacy/<요청번호>.review.json`에만 생성한다. 백업과 삭제 CLI는 같은 설정의 DPAPI 제공자를 사용한다. 경로를 바꿀 때는 기존 삭제 이력도 함께 보존해야 하며 비어 있는 새 이력 폴더로 우회하지 않는다. 채팅·Git·노션에 원문을 붙이지 않는다.
3. `reviewCandidates`는 이름·이메일·전화번호가 남은 필드의 ID/해시 목록이다. 과거 이름·연락처도 `identifiers`에 추가한다. 별도 `sharedContentReview`는 이름 포함 여부와 관계없이 공동 자유문 전체의 행/필드/해시를 담고, `ownedStudentMemos`는 삭제할 개인 메모 행/해시를 담는다. 두 목록에서 행을 임의로 빼지 않는다. 별명·이미지·첨부·문맥상 식별 정보와 실제 작성 경위는 별도로 확인한다.
4. `sharedContentReview`의 모든 항목에 `decision`과 10자 이상의 구체적 `reason`을 적는다. `erase`는 요청자 단독 작성 필드를 빈 문자열로 지운다. `redact`는 혼합 본문 중 요청자 작성 부분을 제거하며, 같은 행/필드/기존 해시의 `redactions`에 검토한 `replacement`를 지정해야 한다. `retain_other`는 요청자 작성 내용이 없고 타인·기관 소유임을 확인한 경우만 선택한다. 법적 보존을 추정해 개인 본문을 남기는 선택지는 없다. 작성 경위가 불명확하면 결정을 비워 두고 완료하지 않는다.
5. `legacyDecisions`의 각 행을 참/거짓으로 확정한다. 다른 사람의 동일 이름을 보존할 때만 `exceptions`에 정확한 행/필드/해시와 10자 이상의 설명을 넣는다. 이 검색 예외는 본문 소유권 결정을 대신하지 않는다. 검토가 끝난 네 가지 확인 항목만 `true`로 바꾼다. 실행 시 전체 후보 목록·개인 메모 목록을 다시 비교해 누락·추가·변경이 있으면 롤백한다. 구형 검토안은 `contentReviewVersion: 1`의 새 조사·결정이 없으면 실행할 수 없다.
6. 최신 암호화 백업을 별도 `newave_privacy_...` 로컬 DB에 복원하고 V004를 적용한다. `PRIVACY_REHEARSAL_DATABASE` 환경변수를 이 이름으로 지정한 뒤 `node tools/privacy/account-deletion.cjs rehearse <보호된 검수안 경로>`를 실행한다. **rehearse는 로컬 DB만 허용하며 전부 롤백한다.**
7. 공동 자료·다른 사람 자료 보존 및 예외 항목을 재확인한다. 유지보수 시간에 백엔드와 작업을 정지하고 진행 중 요청이 끝난 것을 확인한다. 이전 요청이 삭제 후 이름/기록을 다시 쓰지 못하게 하기 위한 필수 단계다. 해당 이용자의 실제 요청을 처리할 권한과 범위를 확인한 담당자만 `node tools/privacy/account-deletion.cjs execute <보호된 검수안 경로> <정확한 요청번호> --maintenance-confirmed`를 실행한다. 이번 개발 검수에서는 이 명령을 운영 계정에 실행하지 않았다.
8. 암호화된 `.pending.dpapi` 삭제 의도를 디스크에 기록/동기화한 후 DB를 커밋하고 `.done.dpapi`로 확정한다. 커밋/파일 확정 실패로 pending이 남으면 완료로 안내하지 않는다. 요청과 DB의 현재 상태를 확인해 담당자가 복구한다. pending을 무조건 지우거나 같은 요청을 다시 실행하지 않는다.
9. 정상 완료 후 평문 검수안은 제거되고 암호화 이력만 남는다. 기존 토큰·재승인 차단, 개인 자료 제거, 공동 집계 보존을 확인한다. 백업과 외부 사본의 잔여 처리 사항을 포함해 신청자에게 결과를 알린다. 실제 메일 발송은 별도 사용자 지시가 있어야 한다.

## 복원·이력 보관

백업 원본 건수/해시 대조 후 `replayLedger`로 확정된 삭제를 복원 DB에 재적용한다. 미완료 의도나 복원 데이터와 검수안의 불일치가 있으면 중단하고 복원본을 운영에 연결하지 않는다. 오래된 DB에 V004가 없으면 먼저 필요한 스키마를 적용하고 새로 검수한다.

삭제된 사용자 행이 없어도 개인 메모의 원래 행 ID와 삭제/부분 삭제한 본문 필드를 대조한다. 이름이나 작성자 ID를 지운 본문이 되살아나도 통과시키지 않는다. 검토 당시와 다른 정상 편집본 역시 자동으로 보존/삭제하지 않고 별도 대조한다. 소유권 결정이 없는 구형 암호화 이력은 재검토가 필요하며, 원래 이력을 임의로 삭제하거나 새 버전 번호만 붙여 우회하지 않는다.

삭제 이력에는 요청 ID·계정 ID·생성시각·식별 문자열·검토안이 포함되므로 개인정보다. DPAPI로 암호화하고 담당자만 접근한다. 관련 백업/외부 사본이 모두 만료·삭제됐는지 확인한 뒤 담당자가 이력도 제거한다. pending·미완료 요청을 나이만 보고 자동 제거하지 않는다. 이력 손실 또는 다른 PC로 이전 시에는 복원 서비스를 열기 전에 담당자의 별도 대조가 필요하다.

이번 작업은 운영 계정 삭제를 실행하거나 운영 완료 이력을 만들지 않았다. 운영 이력 폴더를 조회·복호화하지 않았으므로 과거 다른 작업의 이력까지 없다고 단정하지 않는다. 구형 이력의 존재 여부는 다음 백업 복원 검증(자동 예약 검사 포함)이나 첫 운영 삭제 전 담당자가 보호된 위치에서 파일 유형·건수 등 최소 정보로 확인한다. 공개 출시 준비만을 위해 민감한 이력 본문을 미리 열 필요는 없다. 존재하는 구형 이력은 원본을 보존하고 위 새 소유권 검토 절차에 따라 별도 대조하며, 새 계약이 없는 이력 때문에 복원 검증이 중단되면 데이터 손실로 단정하거나 원본 이력을 지우지 않는다.

## 점검 결과

가상 PostgreSQL 검수에서 개인 계정/TTS/교사 행사 기록 제거, 학생·공동 보고서 보존, 반 집계 유지, 과거 보고서 텍스트 정리, 검토 미완료/대상 변경/알 수 없는 FK/마지막 관리자 차단과 전체 롤백을 확인했다. 백업 만료 및 삭제 의도 기록·재적용의 Node 검사도 통과했다. 상세 최종 결과는 노션 작업로그에 기록한다.

2026-10-16 본문 처리 보완은 운영 백업을 사용하지 않은 새 합성 PostgreSQL DB 두 개에서 검증했다. 실제 삭제 SQL을 실행하는 `PrivacyDeletionTest` 1개와 Node 검사 8개가 모두 통과했고 두 DB는 제거했다. 이름 없는 대상 개인 메모 삭제·타인 메모 보존, 과거 익명 메모의 명시적 결정, 작성자 없는 행사/회의록 삭제·부분 삭제, 공동 상태·집계 보존, 결정 누락·검토 후 새 행/본문·충돌 시 전체 롤백, 삭제된 사용자 없는 복원본의 개인 메모·본문 재등장과 보존 판단 해시 변경 차단을 확인했다. 실제 운영 계정의 삭제 실행이나 실제 iPhone 삭제 성공을 뜻하지 않는다.

공개 삭제 접수 보완을 포함한 별도 백엔드 전체 검증은 총 169개 중 157개 통과·선택 PostgreSQL 검사 12개 건너뜀이다. 위 실제 PostgreSQL `PrivacyDeletionTest` 1/1과 Node 8/8은 별도 실행 증거이며 전체 검사에 12개가 모두 실행됐다고 합산하지 않는다. 11:39 KST 최신 검증은 만 14세 이상 가입 확인을 포함하며 프론트 검사도 109개 통과했다. 배포나 실제 Apple 기기 검수 성공을 뜻하지 않는다.

2026-10-16 TestFlight 1.0.0(2)에서는 사용자 보고로 Apple 인증 후 선택 화면 복귀와 기존 계정 연결·로그아웃·Apple 재로그인을 확인했다. 합성 화면·서버 검사에서는 비밀번호 없는 가입과 삭제 재인증·취소 경로를 확인했지만, 실제 iPhone의 Apple 신규 가입·이메일 가리기·철회 알림·삭제 접수·완전 삭제는 아직 확인하지 않았다. 두 번째 iPhone 확보나 다른 개인 Apple 계정 사용을 Apple의 필수 제출 절차로 취급하지 않는다. 현재 기기로 가능한 확인과 독립된 합성 검사를 진행하고 실제 미확인 항목을 따로 남긴다. 상세 증거는 [Apple 로그인 체크포인트](ios-store/apple-login-checkpoint-2026-10-16.md)를 따른다.
