# TTS 통계 성능 개선 검수

## 변경

기존 집계는 연간 기록과 답변·질문·교사 객체를 모두 로딩하고 매 기록마다 당시 배점 규칙을 만들었다. 통계 쿼리를 기록 ID, 교사 ID, 주차, 질문 ID, 답변 값만 반환하도록 바꾸고, 관리 시작 이전 주차를 DB 조회에서 제외했다. 주별 배점은 요청 안에서 재사용한다. 비활성 교사의 반 정보는 일괄 조회하며, 연간 수동 항목만 있으면 불필요한 회의·기도모임 연동 조회를 생략한다.

시트 점수 우선, 동명이인 연결 방지, 과거 배점, 수동 완료, 빈칸과 0점 구분을 유지한다. 점수를 요청 사이에 캐시하지 않아 다음 조회는 변경된 답변을 반영한다. 주간/분기 통계도 같은 집계 경로를 사용한다. 주간 상세에서 연간 참가자 목록을 유지하는 동작은 변경하지 않았다. DB 스키마·운영 데이터 이관은 없다.

## 자동 검사

- 백엔드 `build bootReviewJar`: 69개 중 실행 62개 성공, 환경 전용 7개 제외. 환경 전용 마이그레이션 검사는 CI PostgreSQL 17/18에서 별도로 실행한다.
- 프런트 73개 성공. 프런트 화면·APK 코드는 이번에 변경하지 않았다.
- 신규 회귀: 52주 기록, 비활성 교사, 답변 없는 0점 기록, 미기록 교사, 중복 답변, 체크 해제 즉시 반영. 연간 조회 시 TtsRecord/TtsAnswer 객체를 로딩하지 않고 쿼리 수가 교사 수에 따라 늘어나지 않는지 확인.
- 기존 회귀: 시트의 공란·0점, 동명이인, 분기·연도 경계, 과거 배점 및 연결 항목, 출석 공동 제출, 행사 당시 명단, 심사/운영 격리 통과.
- 심사 JAR: 실제 명단/개인 키 제외, 합성 초기 자료와 초기 설정 차단 등록 확인.

## 동일한 합성 100명 부하 비교

도구 `tools/loadcheck/run.ps1`, 로컬 PostgreSQL 18.6, JVM 힙 512MiB, JVM에 보이는 CPU 2개. 매 실행 동일한 가상 교사 100명·50반·학생 500명, 과거 TTS 13주를 생성하고 7,302요청·502개 최종 결과를 확인했다. 기존 기준 실행과 개선 후 2회 모두 오류 0, 결과 일치, 중복 기록 0.

## 한계와 다음 검수

이것은 로컬 합성 자료·루프백 통신 검사다. JVM 힙 제한은 Railway 컨테이너 전체 메모리 제한과 다르다. 실제 휴대폰 렌더링, 외부 네트워크, 장시간 부하를 포함하지 않는다. 향후 전체 52주×100명 자료의 부하 검수와 실제 컨테이너 메모리/DB 대기를 관찰한다. 운영에서 테스트용 출석·TTS 기록을 생성하지 않았다.

배포 완료 여부는 노션 작업로그와 실제 Railway 배포 상태에서 별도로 확인한다.
